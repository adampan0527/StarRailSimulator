# 代码规范

本规范适用于 StarRailSimulator 的源码、测试和构建脚本。目标是让后续维护者能定位一条规则、判断改动影响，并复现问题。规范与调研建议不一致时，以规范为准。

按任务补充阅读：

- 修改战斗、角色机制、版本数据、回放或优化器：[模拟与游戏数据规范](simulation-standards.md)。
- 修改任何用户可见的界面：[前端设计规范](design.md)。
- 了解技术决策背景：[技术选型调研](technology-research.md)。

## 模块边界

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| Rust 战斗核心 | 校验指令、推进状态、结算技能、产出事件 | 不依赖 Tauri、数据库、文件系统或网络；输入由调用方提供，可独立测试。 |
| Rust 优化器 | 生成候选打法与配装、调用核心、排序和报告进度 | 依赖战斗核心；不复制战斗公式，不直接读写用户存档。 |
| 应用与存储 | 管理全局角色档案、队伍、版本数据、模拟会话和后台任务 | 向核心提供已校验的输入；数据库访问和文件操作留在适配层。 |
| Tauri 与前端 | Tauri 命令和事件负责传输；前端负责交互、显示和本地表单状态 | 命令委托给应用层；前端不再实现战斗判定、属性计算或库存约束。 |

按业务能力组织代码，如角色档案、行动顺序、状态效果和配装搜索。先用模块划清职责；确有独立测试、构建或依赖隔离需求时再拆 crate。避免循环依赖，也避免用 `utils` 或一个集中式角色分支收纳互不相关的逻辑。

## 通用写法

- 用稳定的领域词汇命名。区分关卡轮次 `cycle`、单位回合 `turn` 和指令 `action`；同一概念在代码、接口与文档里保持一致。易混淆的单位在类型或字段名中标明，例如 `elapsed_ms`。
- 保持最小公开接口和明确的数据所有权。函数围绕一个业务目的组织；复杂条件优先提取成具名判定。抽取确实共享同一规则的逻辑；两个暂时相似、但独立演变的机制可以各自保留。
- 注释说明原因、前置条件、特殊结算时机和兼容承诺。非显而易见的对外接口记录单位、失败条件及副作用。注释不能替代对关键行为的测试。
- 把行为改动与大面积重排、无关格式化或依赖升级分开。跨模块接口、运行时依赖或存档兼容策略发生变动时，在 `docs/` 记录决策理由与影响。

## Rust

- 统一使用 `rustfmt`；模块和函数用 `snake_case`，类型用 `PascalCase`。默认用私有可见性，只在模块边界公开调用方需要的类型和方法。
- 用枚举表示互斥状态，用专用类型区分容易传错的 ID、单位和数值范围。关键规则枚举尽量显式匹配每个分支，避免新变体被默认分支静默吞掉。
- 默认借用；确实需要存储、跨任务转移或隔离快照时再取得所有权或复制。先使用普通数据结构和函数，按实际需要引入 trait、泛型或共享可变状态。
- 可恢复错误使用 `Result`；`Option` 表示预期缺省。规则、导入、保存和任务错误在模块边界保留可区分的类型及上下文。生产输入失败不使用 `unwrap`、`expect` 或 `panic!`；测试夹具可以用这些方法在假设不成立时尽早失败。
- 战斗核心和优化器使用安全 Rust。确需和系统接口交互时，把必要的 `unsafe` 限制在适配层小范围内，记录 `SAFETY` 前提并审查调用约束。

## Tauri 接口与前端

- 在命令、存档和文件导入边界校验输入；区分 IPC 请求/响应、持久化结构与内部领域模型。接口只暴露界面需要的数据，错误传稳定代码和必要字段，由界面映射为用户能理解的提示。异步命令也不得直接承载长期 CPU 密集循环。[Tauri 命令文档](https://v2.tauri.app/develop/calling-rust/)
- Tauri 调用集中在带类型的客户端适配模块，组件通过功能接口调用。改变命令名、字段或事件结构时，同步更新两端和契约测试。对于占用时间长的任务，用任务 ID 关联进度、取消与结果；界面切换任务后忽略旧任务消息。
- 使用 TypeScript 时启用 [`strict`](https://www.typescriptlang.org/tsconfig/strict.html)；不确定的外部数据先按 `unknown` 接收并校验，避免用 `any` 或类型断言绕过检查。使用 React 时按功能组织组件、状态和测试；能从现有状态推导的数据不另存一份。组件不承担持久化、通信协议或业务规则。
- 区分未保存草稿与已保存的全局档案；保存失败时保留输入。关键界面明确加载、空数据、失败和取消后的状态。视觉、交互和动效遵循 [design.md](design.md)。

## 持久化与依赖

- 全局角色档案由应用层统一写入；队伍引用角色形态 ID，不复制完整档案。新建会话时冻结输入，后续修改全局档案不影响会话和历史回放。把一套优化配装应用给多名角色时作为一次事务提交，避免只保存一部分。
- 数据库结构和用户可导入、导出的格式要有版本。已经发布的迁移不改写；新增迁移以旧版用户样本验证读写。遇到未来版本或不能识别的文件时提示原因并保留原件。
- 项目骨架落地后锁定 Rust 工具链与前端运行环境，提交应用的 Rust 和前端依赖锁文件。新增生产依赖先确认用途、维护状态、许可证和 Windows 支持；为解决一个局部问题引入大依赖时说明取舍。

## 验证与合入

- 测试面向可观察行为和关键约束。纯规则用单元测试；跨模块流程、导入导出和迁移用集成测试；核心用户路径用少量界面测试。修复影响用户或模拟结果的缺陷时，优先补能复现故障的回归用例。避免为简单样式调整增加重复断言。
- 骨架建立后，在 Windows CI 从锁文件安装依赖并执行对应检查。前端提供统一脚本用于格式检查、lint、类型检查、测试和构建；涉及 Tauri 配置或打包的变更验证 Windows 构建与启动。检查缺失或未运行时如实记录。
- Rust 工作区的基础门槛如下。启用可选功能后，按受支持的功能组合补充检查，而不是无条件开启所有 feature。[Clippy](https://doc.rust-lang.org/clippy/usage.html) · [Cargo 测试](https://doc.rust-lang.org/cargo/commands/cargo-test.html)

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

审核改动时确认：职责是否放在正确模块、影响结果的行为是否可复现、公开契约和存档是否兼容、相关规范与已运行的检查是否有记录。
